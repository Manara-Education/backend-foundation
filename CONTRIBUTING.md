# Contributing to backend-foundation

## Branches

```
feature branch ──PR──► develop ──release PR──► main ──tag──► release
```

- **`develop`** is the default branch and where all work lands.
- **`main`** only ever advances through a release PR from `develop`. Nothing is
  developed on it.

Branch names use the prefix that fits: `feat/`, `fix/`, `update/`, `remove/`,
then a kebab-case description — `feat/quiz-attempts`, `fix/re-login-401`.

## Commits and pull request titles

```
[Area Emoji] - Sentence case description.
```

Examples from this repository's history:

```
[Quiz Feature 📝] - Add quiz evaluation, attempts and progression.
[Build & Docker 🐳] - Harden the backend container build.
[Database 🗄️] - Put the schema under Flyway and stop seeding production.
```

Write the body to explain **why**, not what — the diff already says what.

## Before opening a pull request

```bash
./mvnw -B -ntp verify        # compiles, runs the full test suite, packages the jar
```

CI runs exactly this, plus a container build and a startup smoke test. Both must
pass before a PR can merge into `develop`.

Fill in `.github/pull_request_template.md` completely. Mark a section
`N/A — <reason>` rather than deleting it: a reader should be able to tell the
difference between "not applicable" and "not considered".

**Label your PR.** Release notes are generated by grouping merged PRs by label
(`.github/release.yml`). An unlabelled PR ends up under "Other Changes" instead
of the section it belongs in.

## Architecture

Feature-based packages under `com.manara.backend`, each with its own
`controller`, `service`, `repository`, `model`, `dto` and `mapper`. Cross-feature
code lives in `common/`. See `.claude/skills/manara-architecture` for the full
convention.

## Database changes

Migrations live in `src/main/resources/db/migration` as `V<n>__description.sql`.

**Never edit a migration that has been applied anywhere.** Flyway records a
checksum of every file it runs, and changing one afterwards makes that database
refuse to start. Fix a mistake with a new migration.

Production runs `ddl-auto=validate`: Hibernate checks the entity model against
the schema and never alters it. If an entity changes, a migration must change
with it or startup fails.

## Secrets

Never commit one. `.env`, `application-local.properties` and
`application-secret.properties` are git-ignored for this reason.
`application.properties` may only ever contain `${ENV_VAR}` placeholders.

Production values come from the environment, supplied by the deployment.
`.env.example` documents every variable the application reads.

## Dependencies

Dependabot raises updates weekly. Patch-level bumps auto-merge once CI passes;
minor, major and every security update go to a human. Adding a dependency by
hand is a decision worth explaining in the PR description.
